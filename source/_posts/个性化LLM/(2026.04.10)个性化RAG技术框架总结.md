# 个性化RAG技术框架总结

## 一、基础概念

### 1.1 定义
**个性化RAG（Personalized RAG）**是指结合**用户画像信息**（背景特征、历史交互、个人知识库PTKB）与当前查询，从外部文本库中检索与用户高度相关的内容，并生成**符合用户个人偏好和上下文**的回答的系统。

### 1.2 与传统RAG的核心区别

| 维度 | 传统RAG | 个性化RAG |
|mathjax: true
------|---------|-----------|
| **输入** | 仅查询（Query） | 查询 + **用户画像（Profile）** |
| **检索** | 通用语义匹配 | **个性化语义匹配**（考虑用户偏好） |
| **生成** | 标准解码 | 可能包含**个性化冲突解决**（如CAD） |
| **目标** | 事实准确性 | 事实准确性 + **用户偏好对齐** |

5. **生成偏好对齐与冲突解决**：在生成阶段应对“用户画像”、“检索来的支持文档”以及“大模型预训练固化的通用知识”三者发生的冲突与幻觉（如CAD解决的知识冲突）。

## 二、三阶段架构与个性化注入点

基于RAG的标准流程（Pre-retrieval → Retrieval → Generation），个性化可在每个阶段注入：

### 阶段1：输入层（Pre-retrieval）— 查询优化
**核心操作**：在检索前将用户画像融入查询或检索策略。  
- 作用说明：把“用户是谁、偏好什么、当前意图是什么”提前注入查询侧，减少后续检索的语义偏差。

| 注入操作 | 技术实现 |
|mathjax: true
---------|---------|
| **查询改写（Query Rewriting）** | 将用户偏好（如"素食"）显式拼入查询文本 |
| **画像选择（Profile Selection）** | 根据当前查询从PTKB中选择最相关的历史记录 |
| **个性化查询扩展** | 基于用户历史生成同义词或子主题扩展查询 |

**示例**：
- 原始查询："推荐餐厅"
- 改写后："推荐**适合素食主义者**的**川菜**餐厅（用户历史偏好）"

### 阶段2：检索层（Retrieval）— 文档获取
**核心操作**：在检索过程中考虑用户个性化特征。  
- 作用说明：不仅看“与查询是否相关”，还看“与该用户是否相关”，提升召回内容的个体匹配度。

| 注入操作 | 技术实现 |
|---------|---------|
| **个性化索引** | 构建用户专属的向量索引（如PEARL聚类用户嵌入） |
| **迟交互匹配** | 使用ColBERT在token级别匹配查询与画像短语 |
| **重排序（Reranking）** | 利用用户画像对初筛文档进行个性化排序 |

**关键技术**：用户嵌入（User Embedding）、个性化共享索引、知识图谱增强（PARK）

### 阶段3：生成层（Generation）— 答案生成
**核心操作**：在解码生成时确保忠实于用户画像和检索结果。  
- 作用说明：在“内容正确”的基础上做到“表达个性化”，并抑制模型默认知识覆盖用户上下文的现象。

| 注入操作 | 技术实现 |
|---------|---------|
| **上下文增强Prompt** | 将检索结果+用户画像拼入Prompt |
| **对比解码（CAD/AdaCAD）** | 对比"有画像"vs"无画像"的分布，强制遵循画像 |
| **奖励优化生成** | 用个性化满意度作为Reward微调生成策略 |

## 三、本周调研重点：生成时个性化（CAD）

### 3.1 定位
本周阅读的 **CAD（Context-Aware Decoding）** 和 **AdaCAD** 属于**生成层（Generation Layer）**的**测试时干预技术（Test-time Intervention）**，解决**"用户画像 vs 模型参数知识"**的冲突问题。

### 3.2 核心原理

**问题场景**：
- 用户画像："我是素食主义者"
- 模型参数知识："大多数人喜欢吃肉"
- 冲突：模型倾向于推荐荤菜（依赖参数知识），忽略画像

**CAD解决方案**：
通过**对比解码**强制模型优先采信画像信息：

$$
y_t \sim \text{softmax}\left[(1+\alpha)\cdot\text{logit}_{\text{有画像}} - \alpha\cdot\text{logit}_{\text{无画像}}\right]
$$

**动态改进（AdaCAD）**：
使用 **Jensen-Shannon Divergence (JSD)** 动态计算调节系数 $\alpha_t$：
- **高冲突**（画像与模型知识矛盾）：JSD ≈ 1，强力纠正
- **低冲突**（画像与模型知识一致）：JSD ≈ 0，退化为标准解码（避免过度校正）

### 3.3 个性化方法范式说明

- **基于提示工程的个性化**：不改模型参数，直接在输入端把用户信息组织进 prompt，让 LLM 生成个性化 rewrite / expansion。  
- **基于表示的个性化**：不一定显式生成新 query 文本，而是构造一个个性化的 query representation / embedding。  
- **基于奖励优化的个性化生成**：query 仍然由生成模型来写，但优化目标不再只是文本像不像人工 rewrite，而是要对齐检索效果或用户收益。  
- **基于群体参数的个性化**：把个性化知识存到参数里，而不是每次检索时临时检索/拼接。  

CAD 作为测试时干预策略，可与上述方法叠加，缓解“个性化信息在生成阶段被模型通用知识覆盖”的问题。

## 四、总结视图

```text
个性化RAG架构全景：
┌─────────────────────────────────────────────────────────┐
│  输入层 (Pre-retrieval)                                  │
│  ├── 查询改写 ← 范式1（提示工程）                         │
│  └── 画像选择 ← 范式1/2（提示+表示）                      │
├─────────────────────────────────────────────────────────┤
│  检索层 (Retrieval)                                      │
│  ├── 个性化索引 ← 范式2（表示学习）                       │
│  └── 迟交互匹配 ← 范式2（ColBERT）                       │
├─────────────────────────────────────────────────────────┤
│  生成层 (Generation)                                     │
│  ├── Prompt构造 ← 范式1                                  │
│  ├── 【CAD/AdaCAD】← 测试时干预（本周调研）               │
│  │   └── 对比"有/无画像"分布，解决知识冲突               │
│  └── 奖励优化 ← 范式3                                    │
└─────────────────────────────────────────────────────────┘
```

**关键洞察**：个性化RAG的四大范式分布于三阶段中，而生成时的**对比解码（CAD）**是确保个性化信息不被模型“遗忘”的关键技术，特别适用于用户画像与模型通用知识存在冲突的场景。
